# Бюджетница

Дашборд мониторинга орг-структуры компании: дивизионы → отделы → команды, у каждого узла численность,
бюджет и эффективность. Тестовое задание, условия — в [`task/task.md`](task/task.md).

![Дерево орг-структуры](docs/screenshots/step1-tree.jpg)

## Запуск

Одной командой, без предварительной настройки:

```bash
docker compose up --build     # http://localhost:8080
```

Клиент раздаётся Nginx, сервер наружу не публикуется — только во внутренней сети compose. Значения по
умолчанию лежат прямо в `docker-compose.yml`, копировать `.env` не нужно; `.env.example` — для
переопределений (порт, период обновлений, ключ AI).

Для разработки:

```bash
npm install
npm run dev          # сервер :3000 и клиент :8080 одной командой
```

Если в `.env` лежит `ANTHROPIC_API_KEY`, его подхватывает и dev-сервер (`--env-file-if-exists`), и Docker.

Нужен Node 22 (`.nvmrc`). Клиент открывается на http://localhost:8080 и ходит в API через прокси Vite —
тот же origin, что в проде за Nginx.

| Команда             | Что делает                                   |
| ------------------- | -------------------------------------------- |
| `docker compose up` | прод-стек: Nginx + сервер                    |
| `npm run dev`       | поднимает mock-сервер и клиент               |
| `npm run verify`    | typecheck + линтер + тесты (то же, что в CI) |
| `npm test`          | Vitest по трём пакетам                       |
| `npm run build`     | прод-сборка клиента                          |
| `npm run size`      | размер сборки против бюджета 200 КБ gzip     |

### Отладочные состояния

При `MOCK_DEBUG=1` (включён в `npm run dev`) параметры адреса прокидываются в API, и состояния можно
посмотреть руками:

| Адрес          | Состояние               |
| -------------- | ----------------------- |
| `/?delay=3000` | загрузка (скелетон)     |
| `/?fail=1`     | ошибка сервера          |
| `/?invalid=1`  | ответ не проходит схему |
| `/?empty=1`    | пустой ответ            |

## Что сделано

### Этап 01 FOUNDATION

- **Монорепо** npm workspaces: `apps/client`, `apps/server`, `packages/contracts` с общими zod-схемами.
- **Mock-API** `GET /api/org-tree` — плоский массив из 61 узла на трёх уровнях, детерминированный сид.
  Версия данных едет в `ETag`, поддержан условный запрос и `304`.
- **Слой данных** — react-query со stale time 5 секунд, валидацией ответа на клиенте и отменой запроса
  при размонтировании. В кэше лежит готовая модель дерева, а не сырой массив.
- **Дерево** — ветка раскрывается кликом по всей строке (в шеврон целиться не нужно), у каждого узла имя,
  штат и индикатор эффективности; по умолчанию раскрыты корни, то есть видно два уровня.
- **Состояния** — загрузка, ошибка (отдельные тексты для схемы, целостности, HTTP и сети), пустой ответ.
- Стилизация только на styled-components, инлайн-CSS запрещён линтером.

### Этап 02 CORE

- **Агрегаты** по поддереву: сотрудники, бюджет и средняя эффективность, взвешенная по численности.
  Считаются один раз на загрузку данных внутри модели.
- **Таблица**: пять колонок задания, липкая шапка, сортировка по любому столбцу (клик — по возрастанию,
  двойной клик — по убыванию), кнопка возврата к порядку дерева.
- **Поиск** с дебаунсом 250 мс фильтрует **и таблицу, и дерево** и подсвечивает совпадения; путь до
  найденного узла сохраняется.
- **Выделение** общее и двустороннее: клик по строке таблицы раскрывает и показывает узел в дереве, клик
  по узлу дерева прокручивает таблицу к нужной строке.
- **Split-view** от 1280px; ниже — переключатель «Таблица / Дерево» в шапке.

![Таблица и дерево рядом](docs/screenshots/step2-split.jpg)
![Поиск фильтрует оба представления](docs/screenshots/step2-search.jpg)

### Этап 03 POLISH

- **Live-обновления по WebSocket**: сервер шлёт патчи метрик, клиент применяет их **без полного рефетча**.
- **Пересчёт только затронутого узла и его предков** — дельта вверх по дереву, потомки не посещаются.
- **Подсветка изменившихся значений** (~1.5 с) в таблице и в дереве, включая агрегаты предков.
- **Индикатор соединения** в шапке: состояние, обратный отсчёт до повтора и кнопка немедленной попытки;
  переподключение — экспоненциальный backoff с полным джиттером:
  `задержка = random(0, min(30 с, 1 с · 2^попытка))`. Нижней границы у джиттера нет намеренно — первая
  повторная попытка может уйти почти сразу, а растёт вверх именно потолок.
- **Клавиатура** без предварительного Tab: нажатие вверх/вниз сразу входит в список. Стрелки, Home/End,
  PageUp/PageDown, Enter (выделить или снять выделение), Escape (снять выделение); в дереве ещё
  влево/вправо для сворачивания и перехода к родителю. Шевроны вне порядка табуляции — иначе Tab шёл бы
  через каждый узел.
- **Выделение**: клик по строке выделяет узел и раскрывает ветку, но никогда не сворачивает её; повторный
  клик по выделенной строке снимает выделение.
- **Анимация раскрытия** через height transition; при `prefers-reduced-motion` анимаций и подсветки нет.

Живые обновления: подсвечиваются и собственные значения, и агрегаты предков — в том числе колонка
«Бюджет суммарный».

### Этап 04 BONUS

- **Прод-окружение одной командой**: два образа (сервер — бандл esbuild на `node:22-alpine` от non-root,
  клиент — статика за `nginx:alpine`), `docker compose up` без предварительного `cp .env`.
- **Nginx**: `gzip on`, `immutable` для хэшированных ассетов и `no-cache` для `index.html`, SPA-fallback,
  прокси `/api` и `/ws` (`proxy_read_timeout 120s` — больше интервала heartbeat). Ответ API тоже сжимается,
  поэтому nginx помечает `ETag` слабым (`W/"<epoch>.<version>"`) — ревизия в нём цела, парсер снимает
  префикс, условный запрос по-прежнему отдаёт `304`.
- **AI-поиск**: `POST /api/search/parse` превращает запрос вроде «отделы с бюджетом больше 50 млн» в
  структурированный фильтр (zod-схема служит и форматом вывода модели, и валидатором ответа). Фильтр
  подставляется в **тот же предикат**, что и текстовый поиск, поэтому действует и на дерево, и на таблицу.
  Пороги сравниваются с агрегатами — с теми числами, которые видны в строке.
- **Что поняла модель — видно текстом**: бейдж «AI применён» и чипы с условиями. Верить на слово не нужно.
- **Без ключа приложение полностью работоспособно.** Нет `ANTHROPIC_API_KEY`, таймаут, ошибка сервиса,
  ответ не по схеме — всё это `source: 'fallback'`: поиск остаётся текстовым, а причина честно написана
  строкой. Ключ живёт только в env сервера и не попадает ни в бандл, ни в образ клиента.

«отделы с бюджетом больше 20 млн и эффективностью выше 70» → `levels: [department]`, `budget.min: 20 млн`,
`performance.min: 70`:

![AI-поиск: разобранный запрос показан чипами](docs/screenshots/step4-ai-applied.jpg)

### Прочтения условий, которые стоит проговорить

- «Второй уровень открыт по умолчанию»: при загрузке видно два уровня — дивизионы и отделы. Команды
  раскрываются по клику, иначе дерево открыто целиком и сворачивать нечего.
- «Невалидный ответ — ошибка» распространено и на лишние поля: схема узла строгая.
- Нарушение целостности (дубликаты id, сироты, циклы) — тоже ошибка, а не повод показать часть дерева.
- «Бюджет больше 50 млн» в AI-запросе — про **суммарный** бюджет подразделения, то есть про число в строке
  таблицы, а не про собственный бюджет узла.

## AI в разработке

Инструмент — **Claude Code** (модель Claude Opus 5). Полный журнал по задачам — в
[`docs/ai-log.md`](docs/ai-log.md): одна строка на задачу, что сгенерировано и что переписано руками.

**Роль человека — ведущая, а не приёмочная.** Автор задал стек и запреты (React, Vite, TypeScript, zod,
react-query, WebSocket, пересчёт вверх по нодам, exponential backoff, styled-components без дизайн-системы),
нарисовал макет и схему деплоя, выбрал процесс «ветка на этап» и сам мерджит и тегирует. Дальше на каждом
этапе он вычитывал результат и возвращал работу с конкретными замечаниями — почти все правки ниже родились
из них, а не из моей самопроверки.

**Что сгенерировала модель.** Практически весь код и текст: scaffold монорепо и конфигурацию инструментов,
mock-сервер с детерминированным сидом и WebSocket-потоком, контракты на zod, `buildModel` с проверкой
целостности, инкрементальную агрегацию, слой запроса, тему и примитивы, дерево и таблицу, поиск, AI-разбор,
Docker и Nginx, все тесты, ADR и документацию.

**Что на каждом этапе решил или поправил человек.**

- **Этап 00.** Выбор стека целиком. Автор же нашёл дыру в версионировании: при рестарте сервера in-memory
  счётчик обнуляется и может совпасть со старым — из этого выросла ревизия `{ epoch, version }` вместо
  одного числа. По его же требованию план был перепроверен до написания кода.
- **Этап 01.** Порты 8080/3000. «Дерево не должно быть открыто полностью — только до второго уровня».
  «Открытие по клику на строку, чтобы не попадать в кнопку».
- **Этап 02.** Поиск фильтрует оба представления, а не только таблицу. Колонка «Всего сотрудников»
  показывает суммарное число, а не два. Прокрутка таблицы к узлу, выбранному в дереве, — тоже его
  замечание: работало только в обратную сторону.
- **Этап 03.** «После обновления срабатывает scrollTo, хотя не должен» — эффекты зависели от модели,
  которая пересобирается на каждом патче. «Неочевидно работает навигация на клавиатуре» — отсюда вход
  стрелками без Tab и шевроны вне порядка табуляции. Escape, снятие выделения повторным кликом и
  исправление обводки фокуса в дереве — тоже по его замечаниям, с приложенным скриншотом.
- **Этап 04.** Вычитка вскрыла мою ошибку в утверждении про ETag (см. ниже), гонку в AI-поиске и
  отсутствие тестов у фичи поиска. Ключ для проверки живого AI-пути тоже дал автор.

**Что модель нашла и исправила сама.** До кода, при перепроверке плана: `applyPatch`, вернув `null`,
отравил бы кэш через `setQueryData`; подсветка через `key` мигала бы на первой отрисовке; `cancelRefetch`
стоял не в том аргументе; `typescript@latest` и `eslint@latest` несовместимы с линтером. При запуске:
экран ошибки не появлялся вовсе — react-query выставляет `error` только после исчерпания ретраев, а в
неактивной вкладке ставит их на паузу. На этапе 04: `docker compose up` падал на старте без ключа (compose
всегда передаёт пустую строку, а схема требовала непустую), и дефолт `AI_MODEL` в compose расходился с
кодом, причём та модель не понимает `output_config.effort`.

**Где модель ошиблась, а поймал человек.** Я написал в ADR 008 и в README, что Nginx не пересжимает ответ
`/api` и ETag доходит нетронутым, сославшись на `gzip_proxied off`. Неверно дважды: директива управляет
сжатием ответов на запросы, пришедшие через **ещё один** прокси (по заголовку `Via`), а проверка, на
которую я сослался, ходила `curl -I` **без** `Accept-Encoding: gzip`, то есть не воспроизводила браузер.
На деле ответ сжимается и ETag слабый — `W/"<epoch>.<version>"`. Работает это лишь потому, что
`parseRevision` снимает префикс `W/`. Утверждение было уверенным и непроверенным; текст исправлен, а
проверка теперь идёт с тем же заголовком, что шлёт браузер.

**Как проверялся AI-поиск.** Обе ветки прогнаны вживую через Nginx: с ключом («отделы с бюджетом больше
20 млн и эффективностью выше 70» → `levels: [department]`, `budget.min: 20 млн`, `performance.min: 70`;
«команды, где меньше 10 человек» → `headcount.max: 9`, то есть строгая граница переведена во включающую)
и без ключа — текстовый поиск с объяснением причины. Таймаут, ошибка сервиса, ответ не по схеме, пустой
фильтр и гонка «ответ пришёл после правки строки» покрыты тестами.
