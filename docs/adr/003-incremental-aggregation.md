# ADR 003. Агрегация и пересчёт вверх по предкам

Статус: Принято · 2026-09-18

## Контекст

Таблица показывает для каждого узла суммарные показатели по нему и всем потомкам: сотрудники, бюджет,
средняя эффективность, **взвешенная по headcount**. Требования: агрегация считается один раз после загрузки
и мемоизируется (шаг 2); при live-патче пересчитываются только затронутый узел и его предки (шаг 3);
обязателен unit-тест на агрегацию.

## Решение

**Модель**

```ts
type OrgModel = {
  epoch: string; // id запуска сервера; версии сравнимы только внутри эпохи (ADR 004)
  version: number;
  byId: ReadonlyMap<Id, OrgNode>;
  childrenOf: ReadonlyMap<Id | null, readonly Id[]>; // null → корни (дивизионы)
  depthOf: ReadonlyMap<Id, number>;
  aggregates: ReadonlyMap<Id, Aggregate>;
};
type Aggregate = {
  headcount: number; // Σ headcount по поддереву
  budget: number; // Σ budget по поддереву
  perfWeight: number; // Σ performance · headcount по поддереву
  avgPerformance: number | null; // perfWeight / headcount; null при headcount = 0
};
```

Хранится **числитель** взвешенного среднего (`perfWeight`), а не только само среднее — это делает
агрегат аддитивным: агрегат родителя = собственный вклад + сумма агрегатов детей. Все слагаемые целые,
поэтому дрейфа плавающей точки при многократных дельтах нет; деление выполняется только при чтении среднего.

**Полный расчёт (один раз в `buildModel`)** — O(n), без рекурсии: узлы обходятся в порядке убывания
глубины, каждый прибавляет свой агрегат к агрегату родителя. Заодно этот проход выявляет циклы
(узел, до которого не дошли от корней).

**Инкрементальный пересчёт (`applyPatch`)** — для каждого изменения узла `X`:

```
delta = contribution(newX) − contribution(oldX)      // { headcount, budget, perfWeight }
for a of [X, parent(X), …, root]:  aggregates[a] = add(aggregates[a], delta)   // новые объекты
```

O(глубина) на изменение, дети не посещаются вообще. На весь патч — одна поверхностная копия `byId` и
`aggregates` (копия ссылок; сами объекты незатронутых узлов остаются прежними → их строки и ноды не
ререндерятся). Нулевая дельта → ранний выход без новых объектов.

**Мемоизация** обеспечивается тем, что агрегаты — часть модели в кэше (ADR 002): компоненты их только читают.
Производные представления (отсортированные/отфильтрованные строки) — `useMemo` от `(model, sort, filter)`.

Тот же обход вверх по предкам (`byId[id].parentId`, пока не `null`) переиспользуется поиском: фильтр
считает `visible = matched ∪ ancestors(matched)`, чтобы путь до совпадения не рвался. Функция `ancestorsOf`
живёт рядом с моделью и не дублируется по фичам.

**Инвариант для тестов:** для любой последовательности патчей
`applyPatch(model, p).aggregates` ≡ `buildModel(applyToNodes(nodes, p)).aggregates`.

## Альтернативы

- **Пересчитывать всё дерево на каждый патч.** Для 40 узлов незаметно по времени, но прямо противоречит
  требованию и меняет идентичность всех агрегатов → ререндер всей таблицы и ложная подсветка.
- **Пересчёт предка как «сумма по детям».** Тоже корректно, но O(глубина × ветвление) и требует обхода
  детей; дельта проще и быстрее.
- **Хранить только `avgPerformance`.** Среднее неаддитивно — пришлось бы каждый раз спускаться к потомкам.
- **Рекурсивный DFS с мемоизацией.** Риск переполнения стека на глубоком/зацикленном дереве,
  сложнее совместить с проверкой целостности.
- **Мутировать модель на месте.** Ломает обнаружение изменений в React и `memo`.

## Последствия

- Патч-контракт (ADR 004) ограничен изменением метрик узла. Структурные изменения (добавление, удаление,
  перенос узла) инкрементально не применяются — сервер шлёт `reset`, клиент делает рефетч и полный расчёт.
- Поверхностная копия индексов — O(n) по ссылкам; осознанный компромисс ради иммутабельности без
  persistent-структур. Пересчёт значений при этом остаётся O(глубина).
- «Подсветка обновлённых ячеек» сравнивает **отрисованное значение**, а не ссылку: патч, меняющий только
  `performance`, создаёт новый объект `Aggregate` у каждого предка, и колонка «Бюджет суммарный» мигала бы
  с неизменившимся числом (ADR 005).
- `applyPatch` возвращает `null`, если патч ссылается на неизвестный `id`; вызывающий код обязан проверить
  это **до** записи в кэш (ADR 004).
- `headcount = 0` во всём поддереве → средняя эффективность `null`, в UI «—».

## Уточнение по итогам вычитки (2026-09-19)

Обещание «пересчёт стоит O(глубина)» верно для **самих агрегатов**, но не для стоимости патча целиком:
`applyPatch` создаёт новые `byId` и `aggregates` через `new Map(...)`, а это O(n) на каждый патч. На
61 узле незаметно, на десятках тысяч — нет. Честная формулировка: посещается O(глубина) узлов, копируется
O(n) ссылок. Чтобы убрать и второе, нужна персистентная структура (HAMT) вместо `Map`; на объёмах задания
это усложнение не окупается, поэтому оно записано как известное ограничение, а не сделано.

Сохранение ссылок нетронутых узлов задумано в том числе ради подписок по идентичности — но в UI это пока
не использовано: узел дерева берёт модель из контекста, поэтому на патче перерисовываются все узлы, а не
только затронутые. Основание для точечной подписки есть, сама подписка не сделана (README, «Что осознанно
не сделано»).
