# ADR 004. Live-обновления: WebSocket, версии, exponential backoff

Статус: Принято · 2026-09-18

## Контекст

Шаг 3: сервер поддерживает обновления в реальном времени; клиент применяет патч без полного рефетча,
показывает индикатор соединения и переподключается с экспоненциальным backoff. На выбор — WebSocket, SSE
или «умный» поллинг. Нужно не потерять и не применить дважды ни одного изменения, в том числе после обрыва.

## Решение

**Транспорт — WebSocket**, эндпоинт `/ws` (тот же origin; в dev — Vite-прокси, в prod — Nginx с `Upgrade`).

**Версионирование.** Ревизия данных — пара **`{ epoch, version }`**:

- `version` — монотонный счётчик `OrgStore`, каждая мутация = +1;
- `epoch` — идентификатор запуска сервера (`crypto.randomUUID()` при старте процесса). Состояние in-memory:
  после падения/рестарта `version` снова начинается с 0, а данные — с seed, поэтому **версии сравнимы только
  внутри одной эпохи**. Без `epoch` перезапущенный сервер мог бы «догнать» старый номер версии: `hello`
  совпал бы с моделью клиента, `ETag` — с закэшированным в браузере (→ `304` и старое тело), а патчи новой
  жизни с меньшими номерами отбрасывались бы как дубликаты — тихое расхождение данных.

Та же пара уходит в `ETag: "<epoch>.<version>"` HTTP-ответа (ADR 002) — HTTP-снимок и WS-поток сшиваются
по одной ревизии, а смена эпохи гарантированно меняет ETag.

**Контракт (сервер → клиент), zod-схемы в `packages/contracts`:**

```ts
{ type: 'hello', epoch: string, version: number }        // сразу после подключения
{ type: 'patch', epoch: string, version: number,         // версия ПОСЛЕ применения
  changes: Array<{ id: string, updatedAt: string,
                   headcount?: number, budget?: number, performance?: number }> }
{ type: 'reset', epoch: string, version: number }        // структурное изменение → рефетч
{ type: 'ping' }                                         // heartbeat, раз в 15 с
```

Клиент → сервер сообщений нет (только протокольный close).

**Применение на клиенте** (`features/connection`, один экземпляр на приложение):

Порядок проверок: сначала «есть ли вообще модель», затем эпоха, и только при её совпадении — номер версии.

| Событие              | Условие                                         | Действие                                           |
| -------------------- | ----------------------------------------------- | -------------------------------------------------- |
| любое                | модели ещё нет (идёт первая загрузка)           | игнор — снимок придёт с актуальной ревизией        |
| любое                | ревизия неизвестна (нет `ETag`, ADR 002)        | `invalidateQueries(orgTree)`; патчи не применяются |
| любое                | `epoch !== model.epoch` (сервер перезапускался) | `invalidateQueries(orgTree)`; патч не применяется  |
| `hello`              | `version === model.version`                     | ничего — данные актуальны                          |
| `hello`              | версии расходятся                               | `invalidateQueries(orgTree)`                       |
| `patch`              | `version === model.version + 1`                 | `setQueryData(prev => applyPatch(prev, patch))`    |
| `patch`              | `version <= model.version`                      | игнор (дубликат / уже учтено рефетчем)             |
| `patch`              | разрыв (`> model.version + 1`)                  | `invalidateQueries(orgTree)` с `cache: 'reload'`   |
| `patch`              | `applyPatch` вернул `null` (неизвестный `id`)   | `invalidateQueries(orgTree)`; в кэш не пишем       |
| `reset`              | —                                               | `invalidateQueries(orgTree)`                       |
| невалидное сообщение | —                                               | лог + игнор; 3 подряд → переподключение            |

Так кэш инвалидируется **только при реальном расхождении**, а штатный поток изменений не порождает запросов.
Строка «модели ещё нет» стоит первой не случайно: во время первой загрузки `model` — `undefined`, и проверка
эпохи, стоящая выше, давала бы лишний `GET` на каждом холодном старте.

Все инвалидации идут с `cancelRefetch: false`, и это **второй** аргумент вызова:
`invalidateQueries({ queryKey: orgTreeKey }, { cancelRefetch: false })`. Внутри первого объекта опция была бы
молча проигнорирована (это не поле фильтра), осталось бы дефолтное `cancelRefetch: true`, и частый тикер
перезапускал бы запрос снова и снова — ровно то, от чего мы защищаемся. Пока рефетч в полёте, следующие
патчи его не трогают; если снимок успел устареть на патч-другой, следующий патч даст штатный «разрыв» и ещё
один дешёвый рефетч.

**Патч применяется вне апдейтера `setQueryData`.** `applyPatch` возвращает `null`, когда патч ссылается на
неизвестный узел, а `setQueryData` пропускает запись только для `undefined`: вернув `null` из апдейтера, мы
записали бы `null` в кэш со статусом `success`, и первый же читатель `model.byId` упал бы — причём это не
ошибка запроса, экран ошибки её не поймал бы. Поэтому:
`const next = applyPatch(cur, msg); if (!next) { invalidate(); return } setQueryData(key, next)`.
Рестарт сервера для клиента выглядит так: обрыв → backoff → `hello` с новой эпохой → один `GET` → полная
замена модели (подсветка обновлений при полной замене не срабатывает — это не патч).

**Состояния соединения:** `connecting → open → (closed → reconnecting)*`, плюс `offline`. Индикатор в шапке
(`role="status"`): подключено / подключение (спиннер) / нет соединения + «повтор через N с».

**Переподключение — exponential backoff с full jitter:**
`delay = random(0, min(cap, base · 2^attempt))`, `base = 1 с`, `cap = 30 с`. Счётчик попыток сбрасывается
только после того, как соединение прожило ≥ 5 с (защита от цикла «подключился — сразу упал»).
Событие `online` → немедленная попытка; `offline` → таймеры останавливаются. Нет ни одного сообщения
(включая `ping`) 35 с → соединение считается мёртвым, закрываем и идём в backoff. Функция расчёта задержки —
чистая (`shared/lib/backoff`), с инъекцией `random`, покрыта тестами. При размонтировании — `close()` и
очистка всех таймеров.

**Сервер.** Обработчик `@fastify/websocket` 11 имеет сигнатуру `(socket, req)`; отдельный не-WS маршрут
`GET /ws` не регистрируется (дубль маршрута). Апгрейд на незарегистрированный путь виден клиенту как
мгновенный `close` без ошибки — поэтому на сервере пишется строка лога.

**Mock-тикер:** каждые `TICK_INTERVAL_MS` (по умолчанию 3000) меняет метрики 1–3 случайных узлов;
значения остаются валидными по схеме. Отключается `TICK_INTERVAL_MS=0`. Для демо обрывов — dev-эндпоинт,
закрывающий все сокеты.

## Альтернативы

- **SSE.** Проще и с авто-реконнектом, но реконнект браузера не даёт управляемого backoff/индикатора
  (а это явные требования), плюс лимит 6 соединений на HTTP/1.1. Двунаправленность нам не нужна — решающим
  стало управление жизненным циклом.
- **Поллинг с ETag и адаптивным интервалом.** Работает без доп. инфраструктуры, но даёт задержку и
  постоянные запросы; оставлен как естественная деградация: без WS приложение живёт на SWR-ревалидации.
- **Слать полный снимок по WS.** Проще клиент, но противоречит «патч без рефетча» и «пересчёт только предков».
- **JSON Patch (RFC 6902).** Универсален, но избыточен: у нас меняются три числовых поля, типизированный
  патч валидируется zod и напрямую ложится в дельта-агрегацию (ADR 003).
- **Стартовать `version` с `Date.now()`** вместо эпохи. Одно число и монотонность между рестартами, но
  завязка на системные часы (перевод времени, два инстанса) и неявная семантика; `epoch` честно говорит
  «это другой поток изменений».
- **Персистить версию/данные на диск.** Убирает проблему в корне, но БД и хранилище заданием исключены,
  а клиент всё равно обязан переживать потерю состояния сервера.
- **Replay пропущенных патчей по `sinceVersion`.** Экономит один GET после реконнекта ценой буфера и
  логики на сервере; рефетч с ETag достаточно дёшев.
- **socket.io / reconnecting-websocket.** Лишний вес и скрытая логика там, где задание просит показать свою.

## Последствия

- Гонка «снимок vs патчи» закрыта версиями: патч, пришедший раньше снимка, игнорируется, а снимок уже
  содержит его изменения; патч «из будущего» вызывает один рефетч.
- Сервер обязан читать `{ nodes, epoch, version }` атомарно (`snapshot()`), иначе ETag и тело могут разъехаться.
- Падение сервера не приводит к тихому расхождению: любая смена эпохи = один рефетч. Проверяется тестом
  «рестарт с совпавшим номером версии» и вручную (kill сервера → старт → данные в UI равны seed + новые патчи).
- Nginx: `proxy_http_version 1.1`, заголовки `Upgrade/Connection`, `proxy_read_timeout` больше интервала `ping`.
- Подсветка обновлений (fade ~1.5 с) строится на смене **значений**, а не ссылок (ADR 005): агрегат предка
  получает новый объект даже когда его число не изменилось.
