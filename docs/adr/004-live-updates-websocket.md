# ADR 004. Live-обновления: WebSocket, версии, exponential backoff

Статус: Принято · 2026-09-18

## Контекст

Шаг 3: сервер поддерживает обновления в реальном времени; клиент применяет патч без полного рефетча,
показывает индикатор соединения и переподключается с экспоненциальным backoff. На выбор — WebSocket, SSE
или «умный» поллинг. Нужно не потерять и не применить дважды ни одного изменения, в том числе после обрыва.

## Решение

**Транспорт — WebSocket**, эндпоинт `/ws` (тот же origin; в dev — Vite-прокси, в prod — Nginx с `Upgrade`).

**Версионирование.** `OrgStore` на сервере держит монотонный счётчик `version`; каждая мутация = +1.
Та же версия уходит в `ETag` HTTP-ответа (ADR 002) — HTTP-снимок и WS-поток сшиваются по одному числу.

**Контракт (сервер → клиент), zod-схемы в `packages/contracts`:**

```ts
{ type: 'hello', version: number }                       // сразу после подключения
{ type: 'patch', version: number,                        // версия ПОСЛЕ применения
  changes: Array<{ id: string, updatedAt: string,
                   headcount?: number, budget?: number, performance?: number }> }
{ type: 'reset', version: number }                       // структурное изменение → рефетч
{ type: 'ping' }                                         // heartbeat, раз в 15 с
```

Клиент → сервер сообщений нет (только протокольный close).

**Применение на клиенте** (`features/connection`, один экземпляр на приложение):

| Событие | Условие | Действие |
| --- | --- | --- |
| `hello` | `version === model.version` | ничего — данные актуальны |
| `hello` | версии расходятся | `invalidateQueries(orgTree)` |
| `patch` | `version === model.version + 1` | `setQueryData(prev => applyPatch(prev, patch))` |
| `patch` | `version <= model.version` | игнор (дубликат / уже учтено рефетчем) |
| `patch` | разрыв (`> model.version + 1`) | `invalidateQueries(orgTree)` |
| `patch` | модели ещё нет (идёт первая загрузка) | игнор — снимок придёт с актуальной версией |
| `reset` | — | `invalidateQueries(orgTree)` |
| невалидное сообщение | — | лог + игнор; 3 подряд → переподключение |

Так кэш инвалидируется **только при реальном расхождении**, а штатный поток изменений не порождает запросов.

**Состояния соединения:** `connecting → open → (closed → reconnecting)*`, плюс `offline`. Индикатор в шапке
(`role="status"`): подключено / подключение (спиннер) / нет соединения + «повтор через N с».

**Переподключение — exponential backoff с full jitter:**
`delay = random(0, min(cap, base · 2^attempt))`, `base = 1 с`, `cap = 30 с`. Счётчик попыток сбрасывается
только после того, как соединение прожило ≥ 5 с (защита от цикла «подключился — сразу упал»).
Событие `online` → немедленная попытка; `offline` → таймеры останавливаются. Нет ни одного сообщения
(включая `ping`) 35 с → соединение считается мёртвым, закрываем и идём в backoff. Функция расчёта задержки —
чистая (`shared/lib/backoff`), с инъекцией `random`, покрыта тестами. При размонтировании — `close()` и
очистка всех таймеров.

**Mock-тикер:** каждые `TICK_INTERVAL_MS` (по умолчанию 3000) меняет метрики 1–3 случайных узлов;
значения остаются валидными по схеме. Отключается `TICK_INTERVAL_MS=0`. Для демо обрывов — dev-эндпоинт,
закрывающий все сокеты.

## Альтернативы

- **SSE.** Проще и с авто-реконнектом, но реконнект браузера не даёт управляемого backoff/индикатора
  (а это явные требования), плюс лимит 6 соединений на HTTP/1.1. Двунаправленность нам не нужна — решающим
  стало управление жизненным циклом.
- **Поллинг с ETag и адаптивным интервалом.** Работает без доп. инфраструктуры, но даёт задержку и
  постоянные запросы; оставлен как естественная деградация: без WS приложение живёт на SWR-ревалидации.
- **Слать полный снимок по WS.** Проще клиент, но противоречит «патч без рефетча» и «пересчёт только предков».
- **JSON Patch (RFC 6902).** Универсален, но избыточен: у нас меняются три числовых поля, типизированный
  патч валидируется zod и напрямую ложится в дельта-агрегацию (ADR 003).
- **Replay пропущенных патчей по `sinceVersion`.** Экономит один GET после реконнекта ценой буфера и
  логики на сервере; рефетч с ETag достаточно дёшев.
- **socket.io / reconnecting-websocket.** Лишний вес и скрытая логика там, где задание просит показать свою.

## Последствия

- Гонка «снимок vs патчи» закрыта версиями: патч, пришедший раньше снимка, игнорируется, а снимок уже
  содержит его изменения; патч «из будущего» вызывает один рефетч.
- Сервер обязан читать `{ nodes, version }` атомарно (`snapshot()`), иначе ETag и тело могут разъехаться.
- Nginx: `proxy_http_version 1.1`, заголовки `Upgrade/Connection`, `proxy_read_timeout` больше интервала `ping`.
- Подсветка обновлений (fade ~1.5 с) строится на смене ссылок из `applyPatch`, без таймеров в JS.
