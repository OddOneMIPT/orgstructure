# ADR 002. Слой данных: react-query, zod, модель в кэше

Статус: Принято · 2026-09-18

## Контекст

Требования: валидация схемы ответа на клиенте (невалидный ответ — ошибка), кэширование со stale time 5 с,
stale-while-revalidate, отмена запросов при размонтировании, инвалидация только при реальном изменении
данных. Позже (шаг 3) в тот же кэш прилетают WebSocket-патчи, а агрегаты должны считаться один раз и
пересчитываться точечно. `GET /api/org-tree` по условию возвращает **плоский массив** — обёртку с версией
в тело добавить нельзя.

## Решение

1. **Запрос.** `fetchOrgTree({ signal })` в `shared/api`: `fetch` с `AbortSignal` от react-query →
   проверка `res.ok` → `OrgTreeResponseSchema.parse(json)` (zod, `z.array(OrgNodeSchema)`; `performance`
   0–100, `headcount`/`budget` — неотрицательные целые, `updatedAt` — ISO datetime). Ошибки типизированы:
   `HttpError`, `ValidationError`, `IntegrityError` — UI показывает разные тексты, но одно состояние «ошибка».
   Статус `304` обрабатывается **до** проверки `res.ok` (у 304 `ok === false`, иначе «ничего не изменилось»
   превратилось бы в экран ошибки): при наличии `prev` возвращается `prev`, иначе запрос повторяется без
   условных заголовков. В браузере 304 до JS не доходит, но доходит в Node/undici — то есть в тестах.
2. **Ревизия данных** передаётся заголовками: `ETag: "<epoch>.<version>"` + `Cache-Control: no-cache`, где
   `epoch` — id запуска сервера (состояние in-memory, после рестарта счётчик версий обнуляется — см. ADR 004).
   Браузер сам делает условный запрос (`If-None-Match`) и получает `304` без тела. Экономятся только байты
   тела (~10 КБ): при `no-cache` поход в сеть происходит всегда, «бесплатной» ревалидация не становится.
   Парсер ревизии обязан быть терпимым: nginx при сжатии проксируемого ответа помечает ETag слабым, и до
   клиента доезжает `W/"<epoch>.<version>"` — снимаем необязательный префикс `W/` и кавычки, на это есть тест.
   **Если `ETag` отсутствует или не разбирается** (прокси, CORS без `exposedHeaders`, middlebox), ревизия
   считается неизвестной: `epoch` синтетический, `version = -1`, патчи не применяются **никогда**, любое
   WS-сообщение ведёт к рефетчу, в консоль один раз пишется предупреждение. Тихое расхождение данных
   превращается в видимую деградацию.
3. **В кэше лежит `OrgModel`, а не сырой массив.** `queryFn` строит модель: `buildModel(nodes, revision, prev)`,
   `revision = { epoch, version }` из `ETag`. Если ревизия ответа (эпоха **и** версия) равна ревизии модели
   в кэше — возвращается **та же ссылка** (`prev`): подписчики не ререндерятся, агрегаты не пересчитываются. Иначе модель строится заново, переиспользуя неизменившиеся
   объекты узлов и агрегатов из `prev`.
4. **`structuralSharing: false`** — задаётся в `defaultOptions.queries` / `setQueryDefaults(orgTreeKey)`,
   **не** в `useQuery`: патч через `setQueryData` может прийти раньше, чем смонтируется компонент, и тогда
   применяются дефолты клиента, а не опции хука.
   Причина именно такая: мы сами гарантируем идентичность (п. 3) и не хотим лишнего глубокого обхода на
   каждую запись. Расхожее объяснение «`replaceEqualDeep` не умеет в `Map` и заменит модель целиком»
   **неверно**: он короткозамыкает на `a === b`, а у не-plain-объектов просто берёт ссылку из `b`, так что
   вложенные `Map` не теряют идентичность. Флаг здесь — про предсказуемость, а не про спасение от порчи данных.
5. **Откуда берётся `prev`:** `queryClient.getQueryData(orgTreeKey)` внутри `queryFn`, клиент захватывается
   замыканием из `useQueryClient()`. В `QueryFunctionContext` нет `previousData`, а поле `client` появилось
   не во всех минорах v5 — на него не опираемся.
6. **Защита от отката версии.** Пока запрос в полёте, тикер продолжает слать патчи, и модель в кэше может
   уйти вперёд ответа. Записав ответ как есть, мы бы откатили уже применённые патчи, а следующий патч дал бы
   «разрыв» и новый рефетч — под частым тикером это зацикливается. Поэтому в `queryFn`:
   `if (prev && prev.epoch === rev.epoch && rev.version < prev.version) return prev`.
7. **Целостность дерева** проверяется в `buildModel`: дубликаты `id`, ссылка на несуществующего родителя,
   циклы → `IntegrityError` (то же состояние ошибки, что и невалидная схема). Молча «чинить» данные не пытаемся.
   Пустой массив — **не** нарушение целостности: `[]` даёт пустую модель и ведёт в состояние «нет данных».
   Проверка ревизии стоит **первой строкой** `buildModel` и возвращает `prev` до проверки целостности и до
   агрегации — иначе обещание «агрегация считается один раз» не выполняется.
8. **Параметры query:** `staleTime: 5_000`, `gcTime` по умолчанию, `retry: 1`, `refetchOnWindowFocus: true`.
   Пока WebSocket подключён, данные считаются свежими за счёт патчей (ADR 004); фокус/реконнект → обычная
   SWR-ревалидация, которая при неизменной версии ничего не меняет.
   Рефетч, вызванный **разрывом версий**, идёт с `cache: 'reload'` — иначе слой, отдающий тело без
   ревалидации (bfcache, прокси, игнорирующий `no-cache`), вернул бы ту же устаревшую ревизию, WS снова
   сообщил бы о разрыве, и цикл повторился бы. Плюс страховка: если рефетч вернул ревизию не выше той, что
   его спровоцировала, второй раз не инвалидируем, а отступаем.
9. **Состояния UI:** `pending` без данных → скелетон; `error` без данных → экран ошибки с «Повторить»;
   данные есть, но `[]` → пустое состояние; ошибка фоновой ревалидации при наличии данных — данные остаются,
   ошибка показывается ненавязчиво.
   Повторная попытка с экрана ошибки не возвращает полноэкранный лоадер. Одного `isFetching` для этого мало:
   при повторе без данных редьюсер обнуляет не только `status` (в `pending`), но и **`error`**, так что экран
   ошибки потерял бы текст. Поэтому последняя ошибка держится в `ref` (пишется при `isError`, сбрасывается
   при успехе), экран ошибки рисуется по `lastError && !data`, а `isFetching` управляет только спиннером
   внутри кнопки «Повторить».

## Альтернативы

- **Сырой массив в кэше + `select`/`useMemo` для модели.** Structural sharing работает «бесплатно», но
  агрегаты пересчитывались бы целиком на каждый патч (или инкрементальная логика уехала бы в компоненты) —
  противоречит требованию «пересчёт только для затронутого узла и предков».
- **Модель в отдельном сторе, react-query только как транспорт.** Два источника правды и ручная
  синхронизация статусов загрузки/ошибки.
- **Версия в теле ответа (`{ version, nodes }`).** Нарушает контракт из задания.
- **Plain-объекты вместо `Map`.** Не решают проблему: идентичность всё равно нужно контролировать при патчах.
- **Тихо отбрасывать «битые» узлы (сироты, циклы).** Таблица и дерево начали бы показывать разное
  множество узлов; для мониторинга честная ошибка лучше.

## Последствия

- Вся логика идентичности сосредоточена в двух чистых функциях (`buildModel`, `applyPatch`) и проверяется
  тестами: «одинаковая ревизия → та же ссылка», «изменился один узел → остальные объекты те же».
- Компоненты могут безопасно использовать `memo`: пропсы-объекты меняются только у затронутых узлов.
- Формулировать «при той же ревизии никто не ререндерится» нельзя: react-query уведомляет по **читаемым**
  свойствам, а `isFetching` на каждой ревалидации меняется дважды, и компонент-оболочка, который его читает
  (п. 9), перерисуется по определению. Инвариант, который действительно держится и который проверяем в
  Profiler: **строки таблицы и узлы дерева не перерисовываются**.
- Клиент зависит от заголовка `ETag`; в Nginx его нельзя срезать (проверить на шаге 4), CORS в dev —
  `exposedHeaders: ['ETag']` либо Vite-прокси (выбираем прокси, same-origin как в проде). Поведение без
  ETag определено (п. 2), поэтому потеря заголовка деградирует приложение предсказуемо, а не ломает его.
- Критерий приёмки не должен опираться на «увидели 304 в DevTools»: при включённом «Disable cache» их не
  будет. Проверяем отсутствие лишних запросов, а сам 304 — через `curl`.
