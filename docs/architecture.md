# Архитектура

Состояние на этап 01. Документ дополняется на каждом этапе, а не пишется в конце.

## Пакеты

```
apps/client        React + Vite, весь UI
apps/server        Fastify, mock-API (и WebSocket с этапа 03)
packages/contracts zod-схемы и типы, общие для клиента и сервера
```

`packages/contracts` — source-only пакет без шага сборки: Vite, tsx и esbuild потребляют TS напрямую
(ADR 001). Один и тот же `OrgNodeSchema` валидирует ответ на клиенте и проверяется в тестах сервера,
поэтому контракт не может разъехаться между сторонами.

## Слои клиента

```
app       провайдеры, layout, глобальные стили, экранные состояния
features  org-tree (дальше — org-table, search, connection)
entities  org: модель дерева, целостность, обёртка над кэшем
shared    api, ui, lib, config (тема)
```

Импорты идут строго вниз: `app → features → entities → shared`. Фичи не ходят друг в друга — общее живёт
в `entities` и `shared`. Это не соглашение на словах: направления проверяет ESLint
(`no-restricted-imports`), как и запрет инлайн-CSS.

Тема лежит в `shared/config`, а не в `app`: токены нужны всем слоям, а `shared` не имеет права
импортировать `app`.

## Поток данных от API до UI

```
GET /api/org-tree
  │  плоский массив + ETag: "<epoch>.<version>"
  ▼
shared/api/fetchOrgTree
  │  304 → «не изменилось» (проверяется до response.ok)
  │  zod-валидация тела; невалидное — ошибка
  │  разбор ревизии из ETag (терпит слабый W/"...")
  ▼
entities/org/loadOrgModel
  │  берёт прошлую модель из кэша (getQueryData)
  │  отбрасывает ответ старше уже применённого
  ▼
entities/org/buildModel
  │  та же ревизия → возвращает прежний объект целиком
  │  иначе: индексы byId / childrenOf / depthOf, проверка целостности,
  │  переиспользование объектов неизменившихся узлов
  ▼
кэш react-query (в нём лежит готовая OrgModel, не сырой массив)
  ▼
features/org-tree → компоненты читают модель и ничего не вычисляют
```

Ключевое решение — **в кэше лежит модель, а не массив** (ADR 002). Из него следует остальное: агрегаты
(этап 02) считаются один раз при построении модели, а патчи по WebSocket (этап 03) меняют её точечно,
без полного рефетча.

Идентичностью объектов управляем сами, поэтому `structuralSharing` выключен — и выключен в дефолтах
клиента, а не в хуке: патч через `setQueryData` может прийти раньше, чем смонтируется компонент.

## Состояние

Разделено по природе:

- **серверные данные** — только кэш react-query;
- **состояние интерфейса** (раскрытые ветки, дальше выделение, режим панелей, сортировка) — крошечный стор
  на `useSyncExternalStore` с селекторами.

Селекторы здесь не украшение: узел дерева подписывается на собственный `isOpen`, поэтому раскрытие одной
ветки не перерисовывает дерево целиком.

## Надёжность

- Любой вход извне проходит zod-валидацию; невалидное — ошибка с понятным текстом, а не «как-нибудь отрисуем».
- `signal` пробрасывается в `fetch`, поэтому размонтирование отменяет запрос.
- Ошибки типизированы (`HttpError`, `ValidationError`, `NetworkError`, `IntegrityError`) — UI показывает
  разные тексты, состояние одно.
- react-query выставляет `error` только после исчерпания ретраев и вовсе приостанавливает их в неактивной
  вкладке, поэтому экран ошибки читает ещё и `failureReason`, а последнюю ошибку компонент помнит сам:
  иначе повтор запроса показывал бы скелетон вместо ошибки.

## Сервер

Состояние — in-memory `OrgStore` с ревизией `{ epoch, version }`. Наружу отдаются только копии; снимок
атомарен (версия и тело читаются вместе), иначе при работающем тикере заголовок и тело разъедутся.
Отладочные параметры включаются только при `MOCK_DEBUG=1`.
