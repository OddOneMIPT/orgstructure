# Модель данных

Состояние на этап 04: контракт, ревизия, модель дерева, целостность, агрегация, фильтрация,
контракт live-обновлений и контракт AI-фильтра.

## Контракт API

`GET /api/org-tree` возвращает **плоский массив** (условие задания):

```ts
{
  id: string,            // непустой
  name: string,          // непустое
  parentId: string | null,   // null — корень (дивизион)
  headcount: number,     // целое ≥ 0
  budget: number,        // целое ≥ 0
  performance: number,   // 0–100
  updatedAt: string,     // ISO datetime
}
```

Схема **строгая**: лишнее поле — ошибка. zod по умолчанию молча срезает неизвестные ключи, но задание
требует «невалидный ответ — ошибка», а тихо срезанное поле означает незамеченное расхождение контракта.

Пустой массив — валидный ответ и ведёт в состояние «пусто», а не в ошибку.

## Ревизия данных

Обёртку с версией в тело добавить нельзя — формат ответа задан. Поэтому версия едет заголовком:

```
ETag: "<epoch>.<version>"
Cache-Control: no-cache
```

- `version` — монотонный счётчик хранилища, +1 на каждое изменение;
- `epoch` — идентификатор запуска сервера.

**Зачем эпоха.** Состояние живёт в памяти: после рестарта счётчик начинается заново и может совпасть со
старым. Тогда клиент решил бы, что данные актуальны, браузер отдал бы тело из кэша по совпавшему ETag, а
патчи нового процесса с меньшими номерами отбрасывались бы как дубликаты — тихое расхождение. Эпоха
делает версии сравнимыми только внутри одного запуска.

Разбор ETag терпит слабую форму `W/"..."`: nginx помечает ETag слабым, когда сам сжимает проксируемый
ответ. Если заголовка нет или он не разбирается, ревизия считается **неизвестной** — модель строится, но
патчи к ней не применяются никогда (этап 03).

## Модель дерева

```ts
interface OrgModel {
  revision: Revision | null; // null — ревизия неизвестна
  byId: ReadonlyMap<OrgNodeId, OrgNode>;
  childrenOf: ReadonlyMap<OrgNodeId | null, readonly OrgNodeId[]>; // ключ null — корни
  depthOf: ReadonlyMap<OrgNodeId, number>; // корень = 0
  roots: readonly OrgNodeId[];
  aggregates: ReadonlyMap<OrgNodeId, Aggregate>;
}
```

Дети отсортированы по имени русским коллатором. `ancestorsOf(model, id)` даёт путь до корня — этот же
обход используют инкрементальная агрегация (этап 03) и фильтр поиска (этап 02), поэтому он один.

### Порядок работы `buildModel(nodes, revision, prev?)`

1. **Сравнение ревизии — первым делом.** Совпала с `prev` → возвращается прежний объект целиком. Отсюда
   следует «агрегация считается один раз»: ревалидация с той же ревизией не строит ничего заново.
2. Индексация в `byId`; узел, не изменившийся ни в одном поле, **переиспользует объект** из прошлой
   модели. Без этого `memo` на строках и узлах не сработал бы ни разу.
3. Проверка целостности.
4. Списки детей и глубины обходом от корней.

### Целостность

| Нарушение      | Как ловится                                |
| -------------- | ------------------------------------------ |
| дубликаты `id` | второй узел с тем же id при индексации     |
| сирота         | `parentId` не найден в `byId`              |
| цикл           | узел, до которого не дошёл обход от корней |

Любое — `IntegrityError`, то же состояние ошибки, что и невалидная схема. Молча отбрасывать «битые» узлы
нельзя: дерево и таблица начали бы показывать разные множества, а для мониторинга честная ошибка полезнее.

Пустой массив нарушением **не** считается.

## Агрегация

```ts
interface Aggregate {
  headcount: number; // Σ по поддереву, включая сам узел
  budget: number; // Σ по поддереву, включая сам узел
  perfWeight: number; // Σ performance · headcount
  avgPerformance: number | null; // perfWeight / headcount; null при нулевой численности
}
```

**Почему хранится числитель, а не среднее.** Среднее неаддитивно: чтобы получить его для родителя, пришлось
бы каждый раз спускаться к потомкам. `perfWeight` делает агрегат аддитивным — агрегат родителя это его
собственный вклад плюс сумма агрегатов детей. Все слагаемые целые, поэтому многократные дельты (этап 03)
не накапливают погрешность, а деление выполняется один раз при чтении.

**Алгоритм.** Узлы обходятся в порядке убывания глубины, каждый добавляет свой агрегат в агрегат родителя:
O(n), без рекурсии (на глубоком дереве рекурсия рискует переполнить стек). Расчёт живёт внутри `buildModel`,
то есть выполняется **один раз на ревизию данных**; компоненты агрегаты только читают.

Неизменившиеся объекты агрегатов переиспользуются из прошлой модели — на этом держится `memo`, а на
этапе 03 ещё и точечная подсветка обновлений.

**Инвариант для этапа 03:** для любой последовательности патчей инкрементальный пересчёт обязан совпасть с
полным: `applyPatch(model, p).aggregates` ≡ `buildModel(applyToNodes(nodes, p)).aggregates`.

## Фильтрация

Один предикат обслуживает оба представления:

```
matched = { узлы, подходящие под условие }
visible = matched ∪ все предки matched
```

Предки нужны, иначе дерево рассыпалось бы на обрывки, а по таблице было бы непонятно, к какому дивизиону
относится найденная команда. При этом предок **не** считается совпадением: подсвечивается только сам
результат, а раскрываются — пути к нему.

Пока фильтр активен, раскрытие дерева вычисляется из `visible`, а собственный набор раскрытых веток
пользователя не меняется и возвращается после сброса запроса.

С этапа 04 в тот же предикат подставляется структурированный фильтр от AI — фильтрация обоих представлений
при этом не меняется.

## Контракт AI-фильтра

`POST /api/search/parse { query: string }` → всегда `200`:

```ts
{
  source: 'ai' | 'fallback',
  filter: SearchFilter | null,   // не null только при source === 'ai'
  reason: string | null,         // не null только при source === 'fallback'
}
```

`SearchFilter` (схема строгая, все поля обязательны и nullable):

```ts
{
  name: string | null,                                   // фрагмент названия
  levels: ('division' | 'department' | 'team')[] | null,
  headcount:   { min: number | null, max: number | null } | null,
  budget:      { min: number | null, max: number | null } | null,
  performance: { min: number | null, max: number | null } | null,
  sort: { column: SortColumn, direction: 'asc' | 'desc' } | null,
}
```

Смысловые правила контракта:

- **Пороги сравниваются с агрегатами узла**, а не с его собственными значениями: `budget.min = 50_000_000`
  означает «суммарный бюджет подразделения не меньше 50 млн» — то самое число, что стоит в строке таблицы.
- **Границы включающие** с обеих сторон.
- **Условия объединяются по И**; внутри `levels` — по ИЛИ.
- **Узел без данных под пороговое условие не подпадает.** Если у поддерева нет сотрудников, средняя
  эффективность равна `null`, и такой узел не попадает ни в `min`, ни в `max`.
- **Фильтр, где непусто только `sort`, считается пустым**: сортировать есть что, а фильтровать нечего —
  такой ответ уходит в `fallback`.

Эта же схема служит форматом структурированного вывода модели (`zodOutputFormat`) и валидатором её ответа
на сервере, поэтому расходиться им негде (ADR 007).

## Контракт live-обновлений

Поток идёт по WebSocket на `/ws` (тот же origin). Сообщения сервера:

```ts
{ type: 'hello', epoch, version }                    // сразу после подключения
{ type: 'patch', epoch, version, changes: [ ... ] }  // version — уже ПОСЛЕ применения
{ type: 'reset', epoch, version }                    // структура изменилась → рефетч
{ type: 'ping' }                                     // heartbeat раз в 15 с
```

Изменение узла несёт только метрики:

```ts
{ id, updatedAt, headcount?, budget?, performance? }
```

Структурные изменения (добавление, удаление, перенос узла) патчем **не** передаются: инкрементально их
не применить, не пересчитав дерево. Для них есть `reset`.

### Как клиент решает, что делать

Проверки идут строго в этом порядке:

| Условие                                                 | Действие                                                |
| ------------------------------------------------------- | ------------------------------------------------------- |
| модели ещё нет                                          | игнор — снимок придёт с актуальной ревизией             |
| ревизия модели неизвестна (не было разбираемого `ETag`) | рефетч, патчи не применяются                            |
| `epoch` не совпал                                       | рефетч: после рестарта сервера номера версий несравнимы |
| `reset`                                                 | рефетч                                                  |
| `hello`, версия совпала                                 | ничего                                                  |
| `hello`, версия другая                                  | рефетч                                                  |
| `patch`, `version <= текущей`                           | игнор: дубликат или уже учтено                          |
| `patch`, `version === текущая + 1`                      | применить инкрементально                                |
| `patch`, разрыв версий                                  | рефетч                                                  |
| `applyPatch` вернул `null` (неизвестный узел)           | рефетч; в кэш ничего не пишется                         |

Инвалидация вызывается с `cancelRefetch: false` **вторым** аргументом: внутри объекта фильтров эта опция
молча игнорируется, и частый тикер перезапускал бы запрос бесконечно.

### Инкрементальный пересчёт

Для каждого изменения считается дельта собственного вклада узла и добавляется ему и каждому его предку —
O(глубина), потомки не посещаются. Структура модели (`childrenOf`, `depthOf`, `roots`) переиспользуется:
патч её не меняет. Объекты незатронутых узлов и агрегатов сохраняют идентичность, поэтому перерисовываются
только затронутые строки, а подсветка обновлений получает точный сигнал.

Инвариант проверяется тестом на случайных последовательностях патчей с фиксированным сидом:
`applyPatch(model, changes)` ≡ `buildModel(применить те же изменения к узлам)`.

## Показатель эффективности

Пороги: `< 50` — низкая, `50–74` — средняя, `≥ 75` — высокая. Правило доменное и живёт в `entities/org`;
`shared/ui` получает уже готовый тон. Цвет никогда не единственный носитель смысла — рядом всегда число.

## Данные mock-сервера

Сид детерминированный: собственный PRNG и фиксированная базовая метка времени вместо `Math.random` и
`new Date()`. Иначе каждый запуск давал бы другие данные и ломал бы тесты и скриншоты.

Получается 61 узел: 4 дивизиона, 15 отделов, 42 команды — три уровня при требуемом минимуме в 40 узлов.
Собственный `headcount` узла — его управленческий слой, он ненулевой на всех уровнях, поэтому взвешенное
среднее (этап 02) осмысленно и для дивизиона.
